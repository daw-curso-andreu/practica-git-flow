1. Introducción teórica

1.1 ¿Qué es Git?

Git es un sistema de control de versiones distribuido creado en 2005 por Linus Torvalds para el desarrollo del núcleo Linux. Un sistema de control de versiones registra los cambios que se hacen sobre un conjunto de archivos a lo largo del tiempo, de modo que podemos saber quién cambió qué y cuándo, volver a una versión anterior y trabajar varias personas a la vez sobre el mismo proyecto sin pisarse.

Que sea distribuido significa que cada desarrollador tiene en su ordenador una copia completa del repositorio, con todo su historial. Se puede trabajar sin conexión y después sincronizar con un repositorio remoto (en nuestro caso, GitHub) mediante git push y git pull.

Conceptos básicos que usamos durante la práctica:

  • Repositorio: carpeta del proyecto más la base de datos de Git (.git) con todo el historial.
  • Commit: «foto» del estado de los archivos en un momento dado, con autor, fecha y mensaje. Se identifica por un hash SHA-1 (por ejemplo f82e8a6).
  • Áreas de trabajo: directorio de trabajo → staging area (git add) → repositorio (git commit).
  • Rama (branch): línea de desarrollo independiente. Permite trabajar en una funcionalidad sin afectar al resto.
  • Merge: integra los cambios de una rama en otra. Con --no-ff se crea siempre un commit de merge que deja constancia de la rama en el historial.
  • Etiqueta (tag): nombre fijo que marca un commit concreto, normalmente una versión publicada (v1.0).
  • Remoto: copia del repositorio alojada en un servidor (GitHub) que sirve de punto de encuentro del equipo.

1.2 La metodología Git Flow

Git Flow es un modelo de ramificación propuesto por Vincent Driessen en 2010. Define qué ramas existen, de dónde nace cada una y a dónde se integra al terminar. Se apoya en dos ramas principales que viven siempre y en tres tipos de ramas de soporte que se crean y se cierran según se necesitan:

RamaNace deSe integra enPara qué sirve
main——Código en producción. Cada commit de main es una versión publicada y lleva etiqueta.
developmain—Rama de integración: contiene las funcionalidades terminadas para la próxima versión.
feature/*developdevelopDesarrollo de una funcionalidad concreta.
release/*developmain y developPreparar una versión: cambiar número de versión, CHANGELOG y últimos ajustes. Al cerrarla se etiqueta.
hotfix/*mainmain y developCorregir o mejorar urgentemente una versión que ya está en producción. Genera una nueva etiqueta.

Para no tener que escribir a mano todos los git checkout, git merge --no-ff y git tag, existe la extensión git-flow (usamos la edición AVH), que añade comandos de alto nivel: 

git flow init                       # crea main y develop y configura los prefijos
git flow feature start <nombre>    # crea feature/<nombre> desde develop
git flow feature finish <nombre>   # merge a develop
git flow release start <versión>   # crea release/<versión> desde develop
git flow release finish <versión>  # merge a main + tag + merge a develop
git flow hotfix start <nombre>     # crea hotfix/<nombre> desde main
git flow hotfix finish <nombre>    # merge a main + tag + merge a develop

1.3 ¿Por qué utilizamos Git Flow?

  • Trabajo en paralelo sin conflictos: somos tres personas y cada una desarrolla su sección en su propia rama feature/*. Nadie toca develop ni main directamente.
  • main siempre estable: el cliente solo ve código que ha pasado por una release. Lo que está a medias vive en develop o en las features.
  • Versiones identificables: cada entrega queda etiquetada (v1.0, v1.0.1) y se puede descargar o volver a ella cuando se quiera.
  • Correcciones rápidas: con un hotfix se puede mejorar la versión publicada sin arrastrar trabajo sin terminar de develop, y la mejora vuelve también a develop automáticamente.
  • Trazabilidad: los merges --no-ff y los mensajes de commit permiten saber qué funcionalidad introdujo cada cambio y quién la hizo. Es justo lo que el cliente necesita para ver que trabajamos con método.

1.4 Buenas prácticas en los mensajes de commit

Todos los commits siguen la convención Conventional Commits:

<tipo>(<ámbito>): <descripción en imperativo, en minúsculas y sin punto> [Usuario N]

<cuerpo opcional: qué se ha hecho y por qué>

Refs #<issue>
  • Tipo: feat (nueva funcionalidad), fix (corrección/mejora), docs (documentación), chore (tareas de mantenimiento: versión, dependencias…).
  • Ámbito: parte del proyecto afectada (layout, contenido, atributos, estilos, nav, release).
  • Asunto corto (≈ 50-70 caracteres) en imperativo: «añade», «mejora», «adapta».
  • Commits pequeños y atómicos: un cambio lógico por commit (por ejemplo, la página de una sección y el enlace del menú van en commits separados).
  • [Usuario N]: como pide el enunciado, cada mensaje indica qué usuario simulado lo ha hecho. En los merges generados por git-flow lo añade automáticamente un hook prepare-commit-msg.
  • Refs #N: enlaza el commit con el issue de GitHub de esa rama, que es la tarjeta del proyecto.

2. Proceso realizado

A continuación se documenta, paso a paso y con capturas, todo lo que ha hecho cada miembro del equipo. Las capturas de terminal muestran la salida real de los comandos; en el prompt aparece qué usuario los ejecuta y en qué rama está (usuario1@equipo-dev … (develop)).

2.1 Preparación del entorno

Cada miembro del equipo configura su identidad y tiene instalada la extensión git-flow:

git config --global user.name  "Usuario 1 (Andreu Sempere)"
git config --global user.email "163463293+AndreuSempere@users.noreply.github.com"
git flow version        # 1.12.x (AVH Edition)

Además, cada uno añade un hook local para que los commits de merge que genera git-flow también lleven el nombre del usuario: 

# .git/hooks/prepare-commit-msg
#!/bin/sh
if [ "$2" = "merge" ] && [ -n "$USUARIO" ]; then
  sed -i "1s/\$/ [Usuario $USUARIO]/" "$1"
fi

Cada rama de trabajo tiene asociado un issue en GitHub (#1 a #6) con la descripción de la tarea; esos issues son las tarjetas del proyecto.

2.2 Usuario 1: creación del repositorio, Git Flow y estructura inicial

Paso 1Crear el repositorio e inicializar Git Flow

El Usuario 1, el más experimentado, crea el repositorio con un primer commit (el README.md con la descripción del proyecto y la tabla de ramas) y ejecuta git flow init -d, que crea la rama develop a partir de main y deja configurados los prefijos feature/, release/ y hotfix/.

Después crea el repositorio vacío en GitHub y sube las dos ramas iniciales:

git remote add origin https://github.com/AndreuSempere/practica-git-flow.git
git push -u origin main
git push -u origin develop

Paso 2feature/estructuraInicial con el HTML5 Boilerplate

Abre la rama feature/estructuraInicial y añade la plantilla HTML5 Boilerplate v9.0.1 tal cual se descarga, en un commit propio. A continuación implementa la estructura pedida por el cliente: cabecera con el nombre del curso e imagen de fondo, barra de navegación con el enlace a Home, footer y una breve descripción del curso en la parte central. Por último adapta los metadatos del boilerplate (nombre, idioma, página 404).

Usamos --no-ff para que siempre exista un commit de merge (aunque fuera posible un fast-forward) y -k (keep) para conservar la rama de la feature y poder subirla a GitHub como evidencia del proceso. 
git push origin develop feature/estructuraInicial

2.3 Usuario 2: features contingutHTML y atributsHTML

Paso 3feature/contingutHTML

El Usuario 2 actualiza develop (git pull) y abre la rama feature/contingutHTML. Crea la página contenido-html.html con ejemplos de innerHTML basados en el ejemplo de W3Schools (cambiar el texto de un párrafo y generar una lista desde un array), con la explicación del código, y en otro commit añade el enlace en la navegación.

Paso 4feature/atributsHTML

Con la primera feature ya integrada, abre feature/atributsHTML. Añade las imágenes de la bombilla, la página atributos-html.html con tres ejemplos comentados (src/alt, el atributo booleano disabled con setAttribute y getAttribute/setAttribute sobre un enlace) y el enlace en la navegación, cada cosa en su commit. 

git push origin develop feature/contingutHTML feature/atributsHTML

2.4 Usuario 3: feature estilsCSS y release v1.0

Paso 5feature/estilsCSS

El Usuario 3, recién llegado a la empresa, sigue el mismo procedimiento. En feature/estilsCSS crea estilos-css.html, js/estilos.js y css/estilos.css con cuatro ejemplos comentados basados en el ejemplo de W3Schools: style.fontSize, colores con <input type="color">, mostrar/ocultar con display y un modo oscuro con classList.toggle. El enlace del menú se coloca entre «contenido» y «atributos», como en el esquema del cliente.

Paso 6release/v1.0

Con todas las features en develop, el Usuario 3 abre la rama release/v1.0, sube la versión de package.json a 1.0.0 y crea el CHANGELOG.md. Al cerrar la release, git-flow hace el merge en main, crea la etiqueta anotada v1.0 y hace el merge de vuelta en develop. El mensaje de la etiqueta se pasa en un fichero con -f. 

git push origin main develop release/v1.0 feature/estilsCSS
git push origin --tags

2.5 Usuario 1: hotfix/milloresV_1_0

Paso 7Mejorar la sección de contenido en producción

El Usuario 1, encargado de las pruebas, detecta que en la v1.0 el ejemplo 1 de «Modificar contenido HTML» solo se puede ejecutar una vez y que faltaría explicar la diferencia entre innerHTML y textContent. Como el cambio afecta a la versión publicada, abre un hotfix/milloresV_1_0 desde main:

  • Botón «Restablecer» en el ejemplo 1 y aria-live en los resultados.
  • Nuevo ejemplo 3 que compara innerHTML con textContent y explica el riesgo de XSS.
  • Versión 1.0.1 en package.json y en el CHANGELOG.

Al cerrar el hotfix con -T v1.0.1 se etiqueta la nueva versión en main y la mejora se integra también en develop. 

git push origin main develop hotfix/milloresV_1_0
git push origin --tags

2.6 Publicación en GitHub

Tras los push de cada usuario, el repositorio AndreuSempere/practica-git-flow contiene las dos ramas principales, todas las ramas de soporte y las dos etiquetas.

2.7 Proyecto de GitHub (tablero) y colaborador

Se ha creado el proyecto «Práctica Git Flow · Curso JavaScript en el DOM», vinculado al repositorio. Cada feature, la release y el hotfix es un issue (#1-#6) con campos personalizados: Tipo, Responsable, Rama, Origen → Destino, Versión / Tag, Commits, fechas y etiquetas. El tablero agrupa las tarjetas por tipo de rama.

El usuario enminqui2 está añadido como colaborador del repositorio (permiso de escritura; la invitación queda pendiente hasta que la acepte) y del proyecto (rol Write).

2.8 Rama gh-pages y GitHub Pages

La documentación (esta página) está en la rama gh-pages, creada como rama huérfana para que no comparta historial con el código: 

git switch --orphan gh-pages
# index.html + css/ + img/ (capturas) + demo/ (web publicada, v1.0.1)
git add -A
git commit -m "docs: añade documentación del proceso Git Flow [Usuario 1]"
git push -u origin gh-pages

La carpeta demo/ contiene la versión v1.0.1 de la web para que el cliente pueda probarla directamente: abrir la web. En Settings → Pages se publica la rama gh-pages desde la raíz.
